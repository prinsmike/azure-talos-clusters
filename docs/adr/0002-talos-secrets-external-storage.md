# ADR-0002: External Storage for Talos Machine Secrets

## Status

Accepted (partial implementation)

### Implementation Progress

**Completed:**
- `lifecycle { prevent_destroy = true }` to prevent accidental secret regeneration
- `ignore_changes` for `talos_version` to allow version updates without regeneration
- A `secrets_backup_command` output documenting the Key Vault backup procedure
- An `environment` variable for secret naming

**Pending:**
- Full external secret import (limited by the Talos provider)
- State encryption with customer-managed keys (Option B enhancement)

## Date

2025-11-30

## Context

Talos machine secrets (`talos_machine_secrets`) contain the cluster's cryptographic
root of trust:

- Kubernetes CA certificate and private key
- etcd CA certificate and private key
- Service-account signing key
- Bootstrap token

By default these are generated by Terraform and stored in **Terraform state**
(inherent to Terraform's design), and — in prod — also mirrored to Key Vault.

### Problems with the default approach

1. **Secrets in Terraform state**: even though state is encrypted at rest in Azure
   Storage, the secrets are present in plaintext inside the state file. Anyone with
   state access can extract the cluster PKI.
2. **Regeneration risk**: if the `talos_machine_secrets` resource is tainted or
   recreated, new secrets are generated, breaking the existing cluster (mismatched
   PKI across nodes).
3. **State size and backup complexity**: machine secrets add bulk to state, and
   backup depends on either state or Key Vault access.

### Terraform ephemeral values are not a fit

Terraform 1.10 ephemeral values are computed at plan/apply time and never written to
state — but they **regenerate on each apply**, which would give new nodes different
secrets than existing ones. Talos secrets must remain stable across the cluster
lifecycle.

## Decision (options considered)

### Option A — External secret generation (recommended)

Generate Talos secrets **outside** Terraform, store them in Key Vault, and have
Terraform read (not manage) them via a data source:

```bash
talosctl gen secrets -o secrets.yaml
az keyvault secret set \
  --vault-name kv-talos-ops \
  --name "talos-secrets-${ENVIRONMENT}" \
  --file secrets.yaml
rm secrets.yaml
```

```hcl
# modules/talos-config
data "azurerm_key_vault_secret" "talos_secrets" {
  name         = "talos-secrets-${var.environment}"
  key_vault_id = var.operations_key_vault_id
}
```

**Pros:** secrets never enter Terraform state; clear separation of secret generation
from infrastructure; easier disaster recovery (Key Vault is the source of truth).
**Cons:** an extra one-time setup step; secret rotation is manual; the Talos provider
may not fully support importing existing secrets.

### Option B — State encryption with customer-managed keys

Enable Azure Storage customer-managed keys (CMK) for the state backend. Transparent
to Terraform, but the secrets are still in state (just better-encrypted) and the
regeneration risk remains.

### Option C — Hybrid

Combine A (external generation + Key Vault) with B (CMK state encryption) for
defense in depth. Most secure, most complex.

### Option D — Accept current risk

Keep secrets in state (encrypted at rest). Simplest workflow, highest-value target.

## Recommendation

**Option A** is recommended: it removes secrets from state entirely and fits our
pattern of decoupled layers (secrets in Key Vault, read via data sources). Consider
**Option C** for production if additional defense in depth is required.

## Consequences

| Aspect | Default | Option A | Option B | Option C |
|--------|---------|----------|----------|----------|
| Secrets in state | Yes | No | Yes (encrypted) | No |
| State access = compromise | Yes | No | Reduced | No |
| Workflow complexity | Low | Medium | Low | High |
| Audit trail | Limited | Full | Limited | Full |

With external secrets, Key Vault becomes the source of truth, state can be recreated
without losing cluster access, and multi-region DR becomes feasible.
